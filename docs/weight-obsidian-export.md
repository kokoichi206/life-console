# 体重を Obsidian の既存グラフに同期する

`weight_obsidian_export` は、D1 に保存された体重を既存の `weight-trend.csv` に日付でマージし、`weight-data.js` を再生成する runner job。DB が持っている期間は履歴全体とは限らないため、DB にない日付を削除しない。

## データの役割

| ファイル | 同期時の扱い |
| --- | --- |
| `weight-trend.csv` | 既存の日付を保持し、DB の記録を反映。7 日移動平均と窓内の記録数を再計算 |
| その他の `weight-*.csv` | 過去の実測アーカイブとして読み取り、グラフ用データに統合 |
| `recalled-weight.csv` | 記憶による推定値として読み取り、実測とは別系列に出力。ファイルがなければ空の系列 |
| `weight-data.js` | 全実測を `DATA`、推定値を `RECALLED` として再生成 |
| `weight-trend.html` | 既存グラフをそのまま使用 |

グラフへの統合は既存の生成処理に合わせ、`weight-*.csv` をファイル名順に読み、日付が重なれば後のファイルの値を採用する。推定値は実測の移動平均に混ぜない。移動平均は直近 7 点ではなく、その日を含む直近 7 日で計算する。

## 採用する方針と候補

定期同期では、DB にある日の値を DB から更新し、DB にない過去の日付を残す。日別グラフは日本時間で最後に測定した値を採用する。アプリでの記録・訂正を Obsidian へ反映する一方向同期として、この組み合わせを採用する。

| 同日の代表値 | 利点 | 制約 | 今回 |
| --- | --- | --- | --- |
| 最後の測定 | その日の後の測定を自動で反映できる | 朝と夜を記録した日は夜が代表になる | 採用 |
| 最初の測定 | 最初に測った値を日内で維持できる | 後で測り直しても代表値は変わらない | 候補 |
| 日平均 | 同日の全測定を日別の 1 点にまとめられる | 実際には測定していない値になり、既存の実測系列の意味が変わる | 候補 |
| 異なる値があれば停止 | 自動で代表値を選ばず確認できる | 複数測定の日が残る限り定期同期が止まる | 変更前 |

| CSV と DB の同日値が異なる場合 | 利点 | 制約 | 今回 |
| --- | --- | --- | --- |
| DB を採用 | アプリの記録・訂正を次回同期で反映できる | その日の CSV の手修正は次回に上書きされる | 採用 |
| CSV を保持 | 既存ファイルの値を維持できる | アプリで訂正してもグラフに反映されない | 候補 |
| 停止して確認 | どちらを採るか毎回判断できる | 値が食い違うたびに手作業が必要 | 変更前 |

DB にある日を訂正するときはアプリ側を修正する。DB の全測定は残し、代表値の選択は Obsidian の日別グラフへの出力時だけに適用する。

## 同期方式の比較

| 方式 | 過去履歴 | アプリの訂正 | 導入と運用 |
| --- | --- | --- | --- |
| 既存 runner で既存 CSV に日付マージ | DB にない日付・アーカイブを保持 | 同じ日付を更新 | 採用案。既存の schedule / job とグラフを使う |
| Mac の専用定期スクリプトで同じマージ | 同じく保持できる | 同じく反映できる | 同期処理に加えて、実行設定・失敗確認を runner と別に管理する |
| 過去履歴を DB に移行してから全件生成 | 移行済みの範囲を保持 | DB から再生成 | 長期の統一案。過去の実測・推定値の区別と移行照合が先に必要 |

現在の DB だけで既存 CSV を全件置換する方式は、DB にない履歴を失うため採用しない。削除まで同期したくなった場合は、履歴移行または同期元を識別できる仕組みを先に設計する。

## 重複と更新の扱い

- 同じ日付・同じ値は 1 行にまとめる。DB にない既存の日付は保持する。
- 同日の代表値は `occurredAt` が最後の測定。測定時刻が同じなら `recordedAt` が最後の記録、両方同じなら `id` の文字コード順で大きい記録を選ぶ。最後の比較は新しさを意味せず、取得順が変わっても出力を固定するための規則。
- 既存 CSV と DB の同日値が異なる場合は、DB の代表値へ更新する。日付で置き換えるため行は増えない。
- CSV 自体に日付の重複や不正な値がある場合も、ファイル更新前にエラーにする。
- DB の削除は CSV の削除として伝播しない。CSV にのみ存在する過去分と区別できないため。
- 生成内容が同じなら CSV・JS の更新日時を変えない。
- 同じ schedule と対象時刻からのジョブ生成は、既存の idempotency key の一意制約で重複を防ぐ。定期設定自体の二重登録防止は未対応。

CSV と JS は両方の内容を生成して一時ファイルへ保存してから、順に rename する。2 ファイルをまとめたトランザクションではない。途中で保存に失敗した場合は job を失敗として報告し、再実行で CSV と JS を一致させる。

## 設定の保存先

| 内容 | 保存先 |
| --- | --- |
| 同期処理と入力の型 | リポジトリ |
| 実行頻度・次回時刻・データディレクトリの相対パス | D1 の `schedules` |
| 各実行の入力・状態・結果 | D1 の `jobs` |
| vault の実パス | runner の `OBSIDIAN_VAULT_PATH` 環境変数 |
| API と Access の認証情報 | Mac の非公開設定・secret store |

実際の有効化設定、個人のパス、アカウント、実データは seed・設定例・ドキュメントに記録しない。以下は登録形式を示す架空の例。

## 準備

1. `schedules.payload_json` を追加する migration を対象 DB に適用し、API と runner を更新する。既存 schedule は `{}` を引き継ぐ。
2. runner に `OBSIDIAN_VAULT_PATH` を設定する。同期先には既存の `weight-trend.csv` とグラフを用意する。
3. 本番では Cloudflare Access の機械認証と runner token を用意する。取得 API は `GET /api/v1/runner/weights/export` で、runner 認証を要求する。通常画面の 730 件という上限は適用しない。
4. 認証済みの `POST /api/v1/schedules` から設定を登録する。新規作成 API なので、同じ定期設定を繰り返し登録しない。

```json
{
  "name": "体重グラフの同期（設定例）",
  "jobKind": "weight_obsidian_export",
  "interval": "hourly",
  "timezone": "Asia/Tokyo",
  "nextRunAt": "2026-10-01T00:00:00.000Z",
  "coalescing": "skip_if_pending",
  "deadlineSeconds": 7200,
  "payload": {
    "dataDirectory": "data/weight"
  }
}
```

`nextRunAt` は希望する初回日時に置き換える。`dataDirectory` は vault からの相対パス。絶対パス、`..`、`.obsidian` 内のパス、vault 外を指すディレクトリ、データファイルの symlink は使えない。

`interval` は `hourly` / `daily` / `weekly`。定期 job の作成時に `payload_json` をコピーするので、設定変更後も既存 job の入力は変わらない。無効化には対象 DB の `schedules.enabled = 0` を使い、すでに生成された job は別途中止する。

## 実行と確認

既存の Cron が到来済みの schedule から job を作成し、runner が poll して実行する。ローカルの Wrangler は `--test-scheduled` を付け、検証用設定の `assets.run_worker_first` に `/__scheduled` を追加してからそのパスを呼ぶ。通常設定のままでは SPA の HTML が返るため、HTTP 200 だけで実行成功と判断しない。この開発用パスを本番へ追加する必要はない。

`--once` は実行待ち job を 1 件取得するオプションで、schedule からの job 生成は行わない。実行後はジョブ一覧と既存グラフを確認し、過去の期間も残っていることを照合する。

Mac の停止中や長い job の実行中には同期できない。Cron は 5 分間隔なので、指定時刻ぴったりの更新は保証しない。失敗した job の即時再試行は行わず、次の定期実行で再取得する。

## 常駐 runner の配置

体重同期に必要な機械認証は、本番ホストの `/api/v1/runner/*` に限定した Access アプリケーションで設定する。Service Auth の Include は専用 Service Token 1 件だけにし、通常画面の本人用ポリシーは維持する。さらに API の `RUNNER_TOKEN` と runner の `LIFE_CONSOLE_RUNNER_TOKEN` を一致させる。設定登録用の `/api/v1/schedules` は本人用の経路を使う。

Cloudflare の [Access の優先順位](https://developers.cloudflare.com/workers/configuration/cloudflare-access/#understand-access-hierarchy) では、パスに一致するアプリケーションが Worker 全体の設定より優先する。保存後は、専用資格情報で runner API に接続できること、資格情報なしでは拒否されること、通常画面へは専用資格情報だけで入れないことを実際の HTTP 応答で確認する。

ビルド済み runner と本番依存パッケージを一時 worktree 以外へ配置し、LaunchAgent から起動する。秘密値は権限 `0600` の非公開環境ファイルへ保存し、起動スクリプトから読み込む。plist や Git 管理のファイルには秘密値を入れない。Service Token の有効期限は非公開の運用記録に残し、期限前に更新する。

この認証範囲では、`/api/v1/job-reports/*` や他の一般 API へ runner の資格情報だけでは接続できない。agent job など別種の処理を有効化するときは、その処理の送信経路を別途確認する。
