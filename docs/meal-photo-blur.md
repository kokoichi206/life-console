# 食事写真の背景ぼかし

Android で選択・撮影した写真を端末内で処理し、元画像と背景をぼかした画像を保存する。Android・Web の表示時に切り替えられる。料理の領域をタップして選択する操作は挟まない。背景ぼかし自体は LLM やクラウド推論を使わない。初回のモデル取得には Google Play services への通信が必要。

## 写真とファイルの関係

`meal_photos` は従来の写真 ID と元画像の R2 キー・アップロード情報を保持する。ぼかし画像は `meal_photo_blurs` に保存し、`photo_id` を `meal_photos.id` への外部キー兼主キーにする。写真 1 枚につきぼかし画像は最大 1 件で、加工履歴は持たない。

`meals.photo_id` と `additional_photo_ids` は元画像側の写真 ID を参照する。加工前後を追加の撮影写真として登録しないため、写真の枚数・順番・既存の解析入力を保つ。栄養解析は既存の元画像取得経路を使い、表示の切り替えによって解析対象は変わらない。

ぼかしの子テーブルには `photo_id`、`object_key`、`content_type`、`upload_token_hash`、`upload_expires_at`、`uploaded_at`、`created_at` を保存する。画像データ本体は R2 に置く。既存レコードの移し替えは不要で、子行のない写真は保存済み画像だけを表示する。以前に加工画像だけを保存した写真から、未保存の元画像を復元することはできない。

## 保存と取得

元画像は従来どおり `POST /api/v1/meal-photos/upload` で予約し、返された URL に PUT する。ぼかしは `POST /api/v1/meal-photos/:id/blur/upload` に `contentType` を送って予約する。元画像と同じ写真 ID を指定し、返された URL にぼかし画像を PUT する。

R2 へ直接 PUT した場合は `POST /api/v1/meal-photos/:id/blur/complete` で実体の存在を確認し、子行の `uploaded_at` を確定する。Worker 経由では PUT の成功時にも確定する。予約だけの子行は表示切り替えの対象にしない。食事の応答の `blurredPhotoIds` は、アップロード完了したぼかし画像を持つ写真 ID の配列である。

未完了の予約を再送すると同じ子行の token・期限を更新する。完了後の予約は `data: null` を返すため、クライアントは再アップロードせず続行できる。完了したぼかし画像の更新・再生成は扱わない。Android は元画像とぼかし画像のアップロードが完了してから食事を保存し、失敗時は同じ食事の `clientId` で再試行する。

元画像は `GET /api/v1/meal-photos/:id/content`、ぼかし画像は同じ URL の `?variant=blurred` で取得する。ぼかしが未保存・未完了なら 404 を返す。取得するファイルの違いを URL で区別し、表示設定によって元画像 URL の意味を変えない。共有画面は既存の共有トークン付き経路から同じ ID・variant を読み、書き込みは許可しない。runner の取得経路は元画像のままとする。

## 保存後の生成

ぼかし画像が未保存の写真は、Android の食事詳細から『この写真の背景をぼかす』で生成する。保存済みの元画像を取得し、登録時と同じ端末内の領域推定・ぼかし処理で画像を作り、既存の予約・アップロード・完了 API で追加保存する。元画像や食事の写真 ID・順序を更新せず、栄養解析も予約しない。完了済みのぼかし画像は更新しない。Web は保存済み画像の表示切り替えに対応し、生成は Android で行う。

## 表示

未操作の対応写真はぼかしオンで表示する。Android の保存直後はプレビューの選択を引き継ぐ。Android は写真ごとのスイッチ、Web は一覧と詳細で共有する表示スイッチを持つ。ぼかしのない写真は元の保存済み画像を表示し、存在しない加工画像を読みにいかない。

オン・オフは表示中の状態として扱い、DB に設定列を追加しない。閲覧端末間では同期せず、共有画面の閲覧者の表示操作も本人の画面設定を変更しない。強制的な背景非公開機能ではなく、表示を選ぶための機能である。

## 実装上の判断と適用

2026-11-14 に本人が保存後の表示切り替えと背景のアップロード許容を明示し、Grok による DB 設計レビュー後に子テーブル方式の実装を依頼した。固定の元画像・ぼかし画像の役割を分け、既存の写真 ID とアップロード経路を維持するため、ぼかし専用の子テーブルを採用する。食事保存前に両画像を完成させること、表示設定を端末内に留めること、元画像を既存の栄養解析へ渡すことはこの実装の判断である。

追加 migration は `0025_clammy_rage.sql`。生成された SQL と meta を同時に適用する。Android の接続先・ビルド・USB 検証は [Android クライアント](../clients/android/README.md)を参照。
