## 2026-09-09 の方針更新

本人用 API を試す方針が明示されたため、無期限の活動 DB を作る初期案を、表示期間ごとに読み出す構成へ変更して実装する。認証情報のみ暗号化して保存し、活動はページングを完了した期間だけ集計する。実装仕様と接続手順は [Strava 連携](../strava-integration.md)。公開資料の未確定点が解消したという意味ではない。

Grok の再技術レビューは調査途中で実行上限に達したため、具体的なソースを渡したコードレビューに切り替えて完了した。指摘を以下の一次情報とコードで照合し、レビュー出力をそのまま採否判断には使っていない。

| 指摘 | 照合と対応 |
| --- | --- |
| `/oauth/revoke` は公式に存在しない | 現行の公式 Authentication は 2026-06-01 導入の `/oauth/revoke`、Basic 認証、refresh token による解除を明記する。古い `deauthorize` への変更は不採用 |
| 心拍の null / 0 がページ全体を失敗させる | 外部入力の境界で null・欠落・ゼロを未計測として扱う。今回の本人データに実際に含まれるかは未確認 |
| Mutation は onSuccess より先に成功状態になる | インストール済み `@tanstack/query-core@5.102.8/src/mutation.ts` は onSuccess を await した後に success を dispatch する。提案された処理移動は不要。解除中のキャンセル、成功後の削除をブラウザテストで検証 |
| 食事が直近 100 件で欠落する | 期間指定 query を追加済み。日本時間の境界と 101 件の取得を storage テストで確認 |
| infinite query の refetch は並列 | 同バージョンの `infiniteQueryBehavior.ts` は await 付きの順次ループ。並列化の指摘は不採用 |
| 短いページなら停止できる | 公式ドキュメントの空ページまで取得する手順を維持。途中までの合計を完成扱いにしない |

認証更新の排他、期限切れ lease、外部 API の失敗伝達、解除失敗時の接続保持をテストする。本番の Access を通した OAuth と本人の実データは接続設定後の確認事項。

最終の修正内容と一次情報の照合結果を Grok に再提示し、提示範囲に未解決の実装ブロッカーはないとの回答を得た。本番の本人接続は未確認という条件を保持する。

本人の Chrome プロファイルで、未使用の既存 API アプリを Life Console 用に変更し、ローカルの健康画面から認可・実データ取得を確認した。100 件を超える期間のページング、週の選択、再読み込み後の期間・接続の復元を確認し、ランニングの距離・移動時間・ペース・平均心拍を Strava の元記録と照合した。体重と食事はローカルの検証用データ。実アカウントでの期限切れ後の token 更新・接続解除、および配置先での接続は未確認。

## 方針更新前の調査結論

Strava API を本人専用アプリで利用できることは公式 FAQ に明記されている。本人のパフォーマンスを理解するアプリも公式の利用例にある。したがって、分析制限の条文だけから、本人の週次集計まで一律に不可と断定した初回の判断は根拠不足だった。

一方、2026-06-01 発効の API Policy の保存・集計制限と、今回の継続保存・食事や体重との比較の関係は、公開資料だけでは確定していない。API 案もファイル方式への変更も未採用。現時点でアプリ実装・接続・DB 操作は行っていない。

## 対象と確認方法

運動を Strava API から取得して D1 に保存し、体重推移・食事記録と同じ期間で振り返る構成。初回の過去分取得、OAuth、webhook、Cloudflare 上の非同期処理を想定した。

初回の Grok 採否レビューは、実装側がまとめた条文の要約に基づくもので、独立した裏取りではなかった。技術レビューは途中で中断し、技術的な承認として扱っていない。

再調査では公式規約、開発者向け導入文書、FAQ、Strava 担当者の過去の回答を読む。Web ツールとは別の HTTP クライアントでも公式 Policy の HTML を取得し、制限条文が本文に存在することを確認した。Grok にも公式 URL から独立に調査するよう依頼した。

個人の運動記録、認証情報、API 応答は Grok に渡していない。ここには会話やレビューの生ログを転記していない。

## 残る確認点

- 自分の運動だけを扱う、非公開・非商用・非 AI の週次集計への 5.4 の適用。
- 過去の活動を定期的に再取得する一時キャッシュと、5.5 / 6.2 の整合。
- 本人の体重・食事との同期間表示への適用。

Strava への問い合わせは送信していない。元データを無期限に保存する API 案を問題なしとして採用する根拠はまだ揃っていないが、ファイル方式への変更が必須と確定したわけでもない。

## Grok の独立調査結果

公式 URL を起点にした再調査は完了した。本人専用アプリの作成経路はあるが、今回の週次集計・体重食事との比較・継続保存に対する現行 Policy の適用を明確に説明した公開回答は確認できなかった。最初の採否レビューを、独立した裏取りや技術的な承認として扱わない。

7 日は取得したコピーのキャッシュ保持期間であり、活動日の古さや API の取得可能期間ではない。現行 API には過去の活動一覧に加え、本人の直近 4 週間・年初来・通算の統計を返すエンドポイントもある。ただし、統計の対象は Everyone 公開の活動であり、任意の週・非公開活動も含む今回の要求をそのまま満たすものではない。技術的に値を取得できることを、独自集計や無期限保存の許可とは扱わない。

2026-06-01 の公式プログラム改定は、個人用ツールの開発を API の用途として説明し、個人分析向けには MCP も案内している。FAQ の MCP 案内を、本人用 API アプリを禁止する説明と読み替えない。一方で、これらの案内にも今回の保存・比較方法への明確な例外規定は確認できない。

## 本人接続で見つかった実行環境の差

実際の Workers 実行環境では `redirect: "error"` が拒否され、トークン交換前に失敗した。架空の認証情報だけを使う最小 Worker でも再現した。`redirect: "manual"` に変更し、既存の成功ステータス判定でリダイレクト応答を失敗として扱う。認証情報をリダイレクト先へ送らない回帰テストを追加し、修正後の本人接続と `pnpm check` の成功を確認した。
