# カロリー収支の初期表示

## 問題と変更

健康画面は Strava の期間内の活動を空ページまで取得した後で、D1 の保存済み消費カロリーを読み始めていた。表示は直近 7 日でも、取得は体重グラフと同じ期間を待っていた。

接続確認後は活動一覧と保存済みカロリーを並行して取得する。カロリー API に既存の開始日時 `occurredAt` を加え、活動一覧がまだなくても日別の収支を表示できるようにした。DB の列・索引・migration は変更しない。

- 最新一覧の取得中は「保存済みの運動で計算しています」と表示する。
- 最新一覧が失敗しても保存済みの値は表示し、最新情報を取得できなかったことを明示する。
- 保存が空で最新一覧も未取得なら、運動ゼロと決めず収支を未表示にする。接続状態の確認中も未接続とは表示しない。
- 最新一覧がそろったら D1 のカロリーを再取得し、新規活動の取得待ちと、一覧から消えた活動を日別収支へ反映する。
- 活動一覧は購読がなくなってから 5 分保持し、取得後 1 分以内の同じ期間への復帰では再取得しない。接続解除時は関連キャッシュを破棄する。

定期同期は既存の runner が担当する。活動一覧の表示時に新しい活動を登録する既存経路は維持しているため、初回の外部リクエスト自体をなくした変更ではない。

## 確認（2026-09-14）

`pnpm check` が成功した。Storybook の回帰確認には、活動一覧が返らない場合の先行表示、取得失敗時の保存済み表示、保存が空のときに運動ゼロと扱わないこと、取得待ちから実測への更新を含む。

独立したローカル D1 に架空の食事 1 件（1,900 kcal）、運動 1 件（500 kcal）、基準消費量（1,500 kcal）を用意した。Web と API は変更後の実装を使い、Strava の接続状態と活動一覧だけをローカルの架空応答に置き換えた。

活動一覧の応答を 5 秒遅らせたとき、収支 `+100` は画面への移動開始から 418 ms で表示され、その時点では活動一覧の応答は 0 件だった。保存済みのカロリーは実 API/D1 から取得し、開始日時の返却も確認した。これはローカルの単発測定であり、本番の表示時間ではない。

一覧の取得後にカロリーが再取得され、同じ収支になることを確認した。ホームへ移動して健康画面へ戻っても、活動一覧のリクエストは 2 回（データと空の終端ページ）から増えなかった。1280 px と 390 px の表示も確認した。

- 検証画面: http://127.0.0.1:8799/health （ローカルの検証用サーバー起動中、架空データ・Strava の応答は 5 秒遅延）
- 本番の変更後の表示時間: 未確認
- 本番への配置・本番 runner の更新: この変更では未実施
