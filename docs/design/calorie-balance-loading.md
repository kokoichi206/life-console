# 運動データの保存と表示

## 変更の目的

健康画面が Strava の活動一覧を直接取得し、ページング完了後に保存済みカロリーを読み込んでいたため、収支の表示が外部 API の応答を待っていた。運動名・距離・時間なども保存し、運動一覧と収支を DB から読むようユーザーが指定した。

## 保存と同期

- `strava_activities` に ID・運動名・種別・開始日時・距離・移動時間・経過時間・平均心拍数を保存する。同期の一覧応答で内容を更新する。
- カロリーの行と表示項目は D1 batch で保存する。既存のカロリーと取得状態は保持し、取得済みの詳細を再取得しない。
- カロリー行の削除は外部キーの cascade で表示項目にも反映する。接続解除、一覧からの削除、詳細取得の 404 が対象。
- migration `0015_loud_scourge.sql` は表示用テーブル、日付検索の索引、遡りの対象を識別する `includes_activities` を追加する。既存データは削除しない。
- 以前の遡りが完了済みでも、次の定期同期で表示項目の遡りを一度だけ開始する。初回は直近 30 日、その前を 90 日単位で 2009-01-01 まで遡る。進捗が保存された後は再開位置を維持する。

## 画面の読み取り

`GET /api/v1/strava/activities` は D1 を期間・日時と ID の順序で読み、100 件ずつ返す。カロリー API と同期状態 API も D1 だけを読む。表示時には token の更新、Strava 呼び出し、ジョブ予約、運動の書き込みを行わない。

収支は保存済みカロリーの日時で集計するため、運動一覧のページングを待たない。保存済みの値であることと同期状態を示し、未同期の運動が含まれないことを注記する。初回同期前で保存が空の場合は運動ゼロとみなさず、同期を案内する。

「運動を同期」は `POST /api/v1/strava/sync` から表示期間のジョブを依頼する。未完了の同期がある場合は重ねて作らない。取得は runner が実行し、画面は 60 秒ごとに D1 を読み直す。カロリー取得待ちと同期状態は 30 秒間隔。ブラウザの活動キャッシュは 5 分保持し、接続解除時は破棄する。
