# D1 の読み取り削減

2026-09-14 に、本番 D1 の上限通知を受けて調査した。修正前のコードは `a9de92e`。本番データの本文や認証情報は記録せず、集計値と架空データでの検証を残す。

## 実績と原因

Cloudflare Query Insights の直近 24 時間を、合計読み取り行数順に取得した。通知の UTC 日単位とは集計期間が異なるため、通知の使用率との厳密な一致や、アカウント全体の合計とは扱わない。Insights の集計はサンプリングを含む。

| 処理 | 読み取り行数 | 実行回数 |
| --- | ---: | ---: |
| 本番の栄養一覧（現行 SQL） | 2,347,579 | 196 |
| 本番の栄養一覧（旧 SQL） | 130,966 | 14 |
| 本番の監視復旧通知の予約確認 | 870,130 | 39,119 |
| 本番の復旧済み障害に対する通知取消の確認 | 305,085 | 34,709 |

本番の上位 20 クエリの合計は 3,878,006 行、開発環境の上位 10 クエリは 41,478 行だった。実データの件数だけを確認すると、食事 27 件、推定履歴 20 件、ジョブ 454 件（うち栄養解析 27 件）、監視障害 15 件、監視通知 354 件だった。

栄養一覧は食事ごとに最新の推定と解析ジョブを検索する。検索条件に対応する索引がなく、食事ごとにジョブ・推定履歴を全件走査していた。さらに健康画面は解析中でなくても 5 秒ごとに一覧を読み直していた。

監視は 1 件の観測を受信するたびに全監視対象を再判定し、復旧済みの障害も繰り返し検索していた。未解決の障害にだけ索引があり、復旧済みを対象別に検索する索引がなかった。

D1 の読み取りはリクエスト数ではなく走査行数で計上される。索引は読み取りを減らす一方、対象列の保存では索引更新の書き込みを伴う。[Cloudflare の料金説明](https://developers.cloudflare.com/d1/platform/pricing/)、[Query Insights の説明](https://developers.cloudflare.com/d1/observability/metrics-analytics/)。

## 変更

`0013_orange_black_widow.sql` で以下の索引を追加する。既存レコードの削除や業務データの書き換えは行わない。

- `nutrition_estimates (meal_id, analyzed_at)`: 食事の最新推定を検索する。

監視の観測受信時は、外部 CLI の観測なら当該対象だけ、runner の観測なら同じ runner の対象だけを再判定する。runner の応答有無が同じ runner の CLI 通知抑止にも使われるため、この範囲は残す。毎分の保守処理では全対象を判定し、観測が来ない障害と、配送後に受付が確定した通知の復旧も検知する。

| agent の回答受信コマンド | 2 秒 | 5 秒 |

返信案は生成完了を確認するため 15 秒を維持する。操作成功時のキャッシュ無効化と、画面へ戻ったときの再取得も維持する。監視の観測は 2 分、未着判定は 5 分、Cron・runner の実ジョブ取得は毎分のまま。元サービスを同期するスケジュールは変更しない。

### なぜ前回の索引では足りなかったか

栄養一覧は健康画面から通常 60 秒、解析中 5 秒で再取得する。前回の `jobs_kind_created_idx` は栄養解析以外のジョブを除外できるが、食事ごとに別の食事の解析履歴を走査する構造は残っていた。食事数と解析履歴の増加で、1 回の一覧取得の走査量が増える。

今回は個別解析と一括解析を別々に検索し、最大 2 件の候補から作成日時・rowid 順で最新を選ぶ。個別解析は食事 ID、一括解析は未解析写真なら最新の一括ジョブ、解析済み・手入力済みなら推定の保存元ジョブを確認する。写真なし・食事の記録時刻・手入力・同時刻の後着順・保存済み結果の成功表示の条件は維持する。

`jobs_kind_meal_created_idx` は種別・JSON 内の食事 ID・作成日時の式索引。`meals.id` と型の扱いを揃えるため、JSON の抽出値を `TEXT` に cast する。cast なしでは相関比較で従来の種別索引が選ばれることを実行計画で確認した。生成した未適用の migration は、Drizzle Kit が式内のカンマを列の区切りとして誤出力した箇所を修正した。schema と生成 snapshot の一致、SQL の実行は別々に検証する。

監視は毎分の保守処理と観測受信で状態を判定する。復旧通知予約は、既に予約した端末でも過去の受付済み警告を検索して競合 INSERT を繰り返していた。既存の一意索引で復旧予約済みの端末を先に除外する。配送受付と復旧判定が逆順になった端末は、従来どおり後から予約する。復旧済み障害そのものの検索は残るため、その履歴数に対して一定コストになる変更ではない。

### 2026-09-27: 栄養一覧の定期取得を廃止

即時の自動更新は必須ではないため、栄養一覧の通常 60 秒・解析中 5 秒の定期取得を廃止した。本人画面と共有画面の両方に適用する。画面の再表示・復帰・通信再接続では既存の Query の鮮度判定に従って再取得し、保存・解析予約後の invalidation は維持する。一覧と食事詳細に「栄養の結果を更新」を追加し、解析完了はこの操作でも反映できる。手動更新時に入力中のカロリーを上書きしない。

変更通知用の WebSocket、Durable Objects、outbox は追加しない。Strava など栄養一覧以外の定期取得は今回の変更対象に含めない。表示期間に限定した栄養取得は未実装で、今回の SQL 改善後も 1 回の取得対象は全食事。全履歴を対象にする一括解析ボタンの判定との分離が必要なため、定期取得の停止とは別の改善として扱う。

本番で観測した 1,212 回すべての呼び出し元は特定できていない。今回止めるのはコードで確認した定期取得であり、過去の全アクセスがこの経路だったと断定しない。
