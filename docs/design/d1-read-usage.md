### Worker・runner・画面の呼び出し構造

```text
Mac runner
  ├─ ジョブ取得: 60 秒ごと → Worker API → D1 の claim
  ├─ 実行中ジョブの heartbeat: 60 秒ごと → Worker API → D1
  └─ 各監視の観測: 120 秒ごと → Worker API → D1 保存・対象の判定
       runner 自身の観測は同じ runner の全対象を再判定
Cloudflare Worker
  └─ Cron: 毎分 → ジョブの期限・定期予約、監視判定・配送、
                  カレンダー保守・配送、本人確認の通知配送 → D1
ブラウザ
  └─ 表示中の Query の自動更新 → Worker API → D1
```

`apps/runner/src/usecases/runner-loops.ts` と本番設定ではジョブ取得は 60 秒。監視はサービスごとに 120 秒。既定の runner 1 件＋外部連携 6 件がすべて動く場合、Cron の全件判定は 7 × 1,440 = 10,080 回/日、観測による判定は（runner の 7 対象＋外部 6 対象）× 720 = 9,360 回/日になる。合計 19,440 回は構成からの試算であり、今回の実測回数ではない。処理時間や失敗、停止中の連携により実行数は変わる。

前回の SQL は未予約の受付を部分索引から取得するものの、索引には未復旧の警告も残る。その全体を各対象の判定で繰り返し走査していた。実際の `EXPLAIN QUERY PLAN` も `SCAN ... USING INDEX monitor_recovery_pending_idx` だった。索引の存在と、必要なキーだけを検索できることは同じではない。`UPDATE` や `INSERT ... SELECT` も対象を探すための行を読む。

### 今回の修正

障害に `recovery_reservation_pending` を追加する。復旧時に確認待ちへ変更し、対象 ID ごとの部分索引 `monitor_incident_recovery_pending_idx` で候補を引く。その障害の受付済み警告だけから復旧を予約する。予約・警告への予約済みの印・障害の確認待ち解除を同じ D1 batch にする。

警告の配送受付が復旧より遅れた場合は、`finish()` が有効な通知 ID・lease・警告種別を確認し、その障害だけを確認待ちへ戻す。受付保存と同じ batch に含め、古い lease や保存失敗で再確認待ちだけが残らないようにする。確認待ちは次の観測または毎分の保守で処理する。購読解除済みの端末は予約対象に含めず、再登録時に過去の復旧を遡って通知しない。

migration `0024_smooth_mac_gargan.sql` は列と部分索引を追加し、既存の復旧済み障害を一度だけ確認待ちにする。既存の未予約受付を引き継ぎ、確認が済んだ履歴は繰り返さない。初回の移行処理と実際の復旧時には、その障害の警告履歴に応じた読み取りがある。履歴削除や監視頻度の引き下げは行わない。
