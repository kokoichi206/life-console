# Strava と健康画面

本人用の読み取り連携。健康画面は既定で体重のみを表示する。必要なときに「走行距離を重ねる」をオンにして、週ごとの走行距離を棒で重ね、体重の変化と運動量を同じ時間軸で見返す。表示の切り替えは期間を変えず、URL に保持して再読み込みでも復元する。重ねている間は右軸に体重の kg、左軸に走行距離の km を表示する。グラフをタップすると、その時期の体重と週の走行距離を確認できる。「この週のランと食事を見る」で同じ週に絞り、ランニング、ウォーキング、筋トレなどの運動一覧と食事写真・メモを開く。日本時間・月曜始まりで集計し、期間の端の週は「一部」と表示する。

週の走行距離・回数・移動時間、平均体重、食事件数の表は「週ごとの数字を見る」から開く。運動の取得途中・失敗時は棒と週の合計を表示せず、体重グラフは引き続き使える。

体重の推移の下に「カロリー収支」を置き、`基準消費量 + 運動 − 摂取` を日別の棒で示す。運動には Strava の活動ごとの実測消費 kcal を使う。未接続なら運動を含めない収支を出し、その旨を注記する。接続確認後は保存済みの運動カロリーを先に読み、活動一覧の取得を待たず収支を出す。最新の一覧が未取得・失敗なら保存済みの値であることを明示する。保存データもない間は収支を出さず、運動ゼロとは扱わない。

保存済みのカロリー API は活動の開始日時も返し、最新の活動一覧がなくても日本時間の日別集計を行える。一覧取得完了後はカロリーを再取得し、新規活動の取得待ちや削除を表示へ反映する。

## 接続設定

[Strava の API 設定](https://www.strava.com/settings/api) で本人のアプリを作成する。有料プランのアカウントを使い、Authorization Callback Domain は配置先のホストに合わせる。ローカルでは `localhost` を使える。

API の環境変数を 4 項目すべて指定する。ローカルは未追跡の `apps/api/.dev.vars` を使う。配置先では対象 Worker に 4 項目すべてを secret binding として登録する。Worker の配置は [Terraform](../infra/terraform/README.md) が担当し、既存の `secret_text` を保持するため、Wrangler の `vars` や Terraform の tfvars へ複製しない。

| 名前 | 値 |
| --- | --- |
| `STRAVA_CLIENT_ID` | Strava が発行する Client ID |
| `STRAVA_CLIENT_SECRET` | Strava が発行する Client Secret |
| `STRAVA_TOKEN_KEY` | `openssl rand -hex 32` で生成した暗号鍵 |
| `STRAVA_REDIRECT_URI` | Web と同じ origin の `/api/v1/strava/callback`。ローカルは `http://localhost:5173/api/v1/strava/callback` |

Client Secret、暗号鍵、認証コード、token を Git・会話・ログに記録しない。暗号鍵を差し替える場合は、先に接続を解除する。保存済みの接続情報は元の鍵でしか読み出せない。

DB は `pnpm --filter @life-console/db migrate:local` でローカルに適用する。健康画面の `Connect with Strava` から認可し、非公開の運動を含む `activity:read_all` を許可する。書き込み権限は要求しない。配置先では既存の Cloudflare Access による本人認証を維持し、callback も同じ保護範囲に置く。

API アプリは 1 アカウントにつき 1 個という[公式スタッフの案内](https://communityhub.strava.com/developers-api-7/register-an-app-w-o-subscription-3153)がある。別用途の既存アプリを転用する際は、その連携が使われていないことを確認する。

## 取得と保存

- 活動一覧は表示期間ごとにページングし、空ページまで取得してから合計する。取得途中・失敗を走行距離ゼロとして扱わない。
- ランは `Run`・`TrailRun`・`VirtualRun`。ウォーキングや筋トレなどは別の運動として数え、詳細に種別を表示する。ペースは距離と移動時間から計算する。心拍がない記録には値を補わない。
- 体重は保存済み実測値、食事は期間を指定して取得する。期間指定の食事は直近 100 件の制限を使わない。
- 既定は現在までの 90 日。全期間ボタンの開始日は保存済み体重の最古日を使う。さらに古い運動は日付指定で取得できる。
- 活動一覧はブラウザのメモリ内で期間ごとに保持し、購読がなくなってから 5 分後に破棄する。1 分以内の再表示では再取得せず、接続解除時は活動・消費カロリー・同期状態のキャッシュを破棄する。取得結果を HTTP キャッシュに残さない。名前・種目・距離・時間・心拍は保存しない。
- 活動ごとの消費 kcal だけを D1 の `strava_activity_calories` に永続保存し、カロリー収支に使う。保存する項目は活動 ID・開始日時・状態（`pending` / `measured` / `unavailable`）・消費 kcal・登録日時・一覧で最後に見た日時・取得日時に限る。**この永続保存は [Strava API Policy](https://www.strava.com/legal/api_policy) の 6.2（7 日を超える保持の禁止）と 5.5（後から取り出せる形での保存の禁止）に反する。6.3 の 48 時間以内の削除反映も保証できない（定期同期は直近 30 日だけを突き合わせるため、それより古い削除は反映されない）。本人が画面を見ていなくても 2 時間ごとに取得・保存する。本人専用・外部非公開のダッシュボードであることと保存項目を最小限にとどめることを前提に、ユーザーが 2026-09-13 に規約の原文を確認した上で選択した。本書は規約適合を主張しない。**
- 認証情報は D1 の `strava_connection` に AES-GCM で暗号化して保持する。更新・接続・解除は同じ lease で直列化し、期限切れや古い処理の保存を拒否する。
- 取得は 2 時間ごとの定期同期（`strava_calories_sync` の schedule）が主で、直近 30 日を突き合わせる。初回だけ下限日（2009-01-01）まで 90 日ずつ遡り、進捗を `strava_calories_backfill` に持つ。schedule は本人が `POST /api/v1/schedules` で 1 回登録する。`運動を更新` と画面表示は即時の補助として、未取得の活動があれば同じ種別のジョブを予約する。runner が API 経由で詳細を順に取得し、消費 kcal を保存する。webhook は使わない。GPS コースは `View on Strava` から確認する。
- 消費 kcal の取得は API がレート制限を制御する。応答の `X-ReadRateLimit-Limit` / `X-ReadRateLimit-Usage` と `X-RateLimit-Limit` / `X-RateLimit-Usage`（[Rate Limits](https://developers.strava.com/docs/rate-limits/)）から使用率を読み、15 分枠の閾値に達したら次の境界まで待ち、日次の閾値に達したらそのジョブを打ち切る。画面表示の一覧取得も同じ予算を使うため、閾値は上限より手前に置く。取得待ちのまま残った行は次の定期同期で再開する。定期のジョブは待たずに終え、続きを次の周期に回す（runner はジョブを 1 件ずつ実行するため、待つと他の種別が止まる）。
- Strava 側で削除された活動は、ジョブの reconcile が消す。reconcile は一覧をページ単位で読み（Worker の 1 リクエストあたりの subrequest 上限に全ページが収まらないため）、現れた活動の「最後に見た日時」を進める。空ページに達した時点で、期間内の行のうちこのジョブの開始時刻より前にしか見ていない行を削除する。一覧の取得に失敗したときは削除も登録も行わない。詳細取得で 404 が返った活動も消す。画面表示側の登録は削除を行わない（期間全体を見終えたことをページ単位の 1 リクエストでは判定できない）。定期同期は直近 30 日だけを突き合わせる。それより古い削除は、本人がその期間を表示したときの同期でだけ反映される。
- `接続を解除` は Strava の revoke API が成功した後に、保存した認証情報・画面の運動データ・保存済みの消費 kcal・遡りの進捗をすべて消す。失敗は表示し、再試行できるよう接続情報を保持する。再接続後は遡りを初回からやり直す。

## 設計判断と確認範囲

2026-09-09、規約の適用に未確定点があることを確認した上で、本人用 API を試す方針になった。本実装を Strava による個別許可取得済みとは扱わない。

2026-09-14、消費カロリーの取得を 2 時間ごとの定期同期に変え、初回は下限日まで遡ることを決めた。本人が画面を開かなくても取得・保存するため、API Policy 6.2 からの距離はさらに広がる。ユーザーの判断（永続保存の選択）は変わらない。schedule は本設計に含めず、本人が `POST /api/v1/schedules` で登録する。定期同期の状態は健康画面の 1 行に出し、runner が止まっていることに気づけるようにした。

2026-09-13、カロリー収支のために活動ごとの消費 kcal を D1 へ永続保存する方針を決めた。ユーザーが API Policy 6.2・5.5・6.3 の原文を確認した上での選択で、規約に反することを承知している。却下した案は (i) 種目・距離・時間と体重からの MET 概算（Strava アプリの表示と一致しない）と (ii) 直近 7 日だけ実測をキャッシュし以前は概算（同じ日の表示が 7 日を境に変わる）。消費 kcal は `GET /activities/{id}` の `calories` だけを読み、取得できない活動は概算へ落とさず「算入外」として収支から除く。`calories` が省略・null の場合と、`0` かつ `moving_time > 0` の場合を値なしとして扱う規則は実データで未確認。

認証・D1・外部 HTTP の架空応答を用いたテストと、実際の本人アカウントへの接続確認は区別する。実データ確認には上記の接続設定と Strava での認可が必要。

2026-09-09 の検証: `pnpm check` は成功。ローカル D1 に migration を適用し、健康画面の期間変更・再読み込み、食事表示、Strava 未設定表示を確認した。接続後の週次表示・取得途中の失敗・解除は架空応答の Storybook で確認し、390 px のカード表示も実際に確認した。本人の Chrome プロファイルで、未使用の既存 API アプリを Life Console 用に変更し、ローカルの健康画面から認可・実データ取得を確認した。100 件を超える期間のページング、週の選択、再読み込み後の期間・接続の復元を確認し、ランニングの距離・移動時間・ペース・平均心拍を Strava の元記録と照合した。体重と食事はローカルの検証用データ。実アカウントでの期限切れ後の token 更新・接続解除、および配置先での接続は未確認。
